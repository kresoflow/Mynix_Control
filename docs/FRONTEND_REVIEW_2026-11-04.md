## Находки по приоритету

### F01 · P1 · Офлайн-чек одного тенанта отправляется с токеном другого

Место: `frontend/lib/features/pos/services/pos_sync_service.dart:35`,
`frontend/lib/features/pos/services/pos_outbox_service.dart:6`,
`frontend/lib/main.dart:132`.

Шаги: сохранить чек без сети под сессией A, выйти, войти в B и запустить
синхронизацию. Хранилище `pos_outbox` общее, запись не содержит владельца-тенанта,
а сервис использует текущий токен из API-клиента. Фоновая синхронизация запускается
при создании приложения и не останавливается на выходе.

Доказательство: перехвачен POST старого чека с `Authorization: Bearer tenant-b-token`.
Если идентификаторы товаров существуют в B и сервер разрешает операцию, чек может
создаться в B; серверное создание в рамках этого ревью не выполнялось.

Исправление: разделить локальные очереди по тенанту, привязать синхронизацию к
активной сессии, проверять принадлежность записи до отправки. Существующие записи
без владельца не присваивать автоматически новому пользователю.

### F02 · P1 · Данные предыдущей сессии остаются после повторного входа

Место: `frontend/lib/main.dart:247`,
`frontend/lib/features/inventory/bloc/document_bloc.dart:78`.

При выходе сбрасывается только аналитика. Корзина, отложенные чеки, документы,
поставщики и другие общие BLoC продолжают жить в экземпляре приложения.
На новом входе `LoadDocuments()` пропускается, если список уже заполнен.

Доказательство: загрузка A вернула документ 1; после смены контекста на B и события
нового входа остался документ 1, второй запрос вообще не выполнен. Это проверка
клиентского состояния, а не доказательство обхода серверной изоляции.

Исправление: пересоздавать состояние сессии или явно сбрасывать все зависимые BLoC
и кэши на выходе/смене тенанта. Старые незавершённые запросы также не должны
публиковать результаты в новую сессию.

### F03 · P1 · Ошибка проверки PIN открывает финансовые суммы

Место: `frontend/lib/features/auth/repository/auth_repository.dart:111` и `:119`.

В обеих ветках обработки исключений PIN `1234` и `0000` принимается как верный.
Диалог `shift_pin_dialog.dart` использует этот результат для разрешения раскрытия
финансовых сумм. Достаточно ошибки соединения или ошибочного HTTP-ответа.

Доказательство: два теста с недоступным сервером получили `isValid == true`.

Исправление: при любой ошибке проверки возвращать отказ и понятную ошибку.
Приём PIN должен подтверждаться ответом сервера. Это находка о раскрытии сумм
на клиенте; обход серверных прав на денежные операции не проверялся.

### F04 · P1 · Черновик товара привязывается к сырью с совпадающим ID

Место: `frontend/lib/features/inventory/view/widgets/warehouse/dialogs/receive_document/receive_document_processor.dart:34`.

`bindDraftIngredients` ищет по числовому ID без проверки `isRetail`. Сырьё и
розничные товары загружаются в один список, сырьё идёт первым. Их ID принадлежат
разным таблицам и могут совпадать. Результат поиска определяет тип позиции
при следующем сохранении.

Доказательство: черновик с `retail_product_id=1` для воды сопоставлен с мукой
`ingredient_id=1`: ожидался `retail_1`, получен `ingredient_1`.

Исправление: сопоставлять по паре «тип сущности + ID». Поиск по имени не должен
подменять явно заданный идентификатор другой сущностью.

### F05 · P1 · При офлайн-сохранении меняется смысл заказа на столик

Место: `frontend/lib/features/pos/repository/order_repository.dart:75` и `:209`,
`frontend/lib/features/pos/services/pos_sync_service.dart:48`.

Онлайн-запрос содержит `table_number`, `order_source`, `payment_account`, но
офлайн-модель и повторная отправка их теряют. Заказ «В стол, без оплаты» с методом
`cash` после синхронизации отправляется как обычный POS-заказ без номера стола.
Backend выбирает постоплату по `order_source`; без него используется обычная
логика POS (`backend/app/pos/services/checkout_service.py:163`).

Доказательство: перехваченный payload синхронизации не содержит всех трёх полей.

Исправление: сохранять и повторно отправлять исходный контракт заказа полностью,
включая источник, стол и счёт. Для старых записей предусмотреть явную обработку.

### F06 · P1 · Оплата удаляет товар, добавленный во время запроса

Место: `frontend/lib/features/pos/bloc/cart_bloc.dart:288`.

После успешного запроса безусловно очищается текущая корзина. Пока запрос идёт,
добавление и изменение позиций продолжают обрабатываться; элементы каталога
и управления количеством не блокируются общим флагом отправки.

Доказательство: серверу отправлена одна позиция; во время ожидания добавлена вторая;
после ответа в корзине нет ни одной позиции. Второй товар не попал в запрос.

Исправление: зафиксировать снимок оплачиваемой корзины и исключить изменение этого
снимка до завершения либо отделить новые позиции от оплачиваемых. Проверить также
удаление, изменение количества, очистку и переключение отложенных чеков.

### F07 · P1 · Повторное событие оплаты создаёт запрос с новым UUID

Место: `frontend/lib/features/pos/bloc/cart_bloc.dart:190` и `:266`,
`frontend/lib/features/pos/repository/order_repository.dart:23`.

Обработчик не проверяет `isSubmitting`, события обрабатываются конкурентно,
каждый вызов Repository создаёт новый `client_uuid`. Отключение кнопки после
перестроения интерфейса не защищает сам обработчик от уже поступивших событий.

Доказательство: два события до ответа первого запроса создали два POST с разными
UUID; серверная идемпотентность по UUID не объединит такие запросы.
Проверка выполнена на уровне BLoC; частота воспроизведения физическим двойным
нажатием на устройстве не измерялась.

Исправление: отклонять повторную отправку на уровне BLoC, применять подходящий
трансформер и сохранять один ключ идемпотентности для одной логической операции.
Одна только последовательная обработка не означает отбрасывание повторов.

### F08 · P2 · WebSocket-события не обновляют заполненный журнал документов

Место: `frontend/lib/features/inventory/bloc/document_bloc.dart:44` и `:78`.

Обработчик событий создания/проведения посылает `LoadDocuments()` без
`forceRefresh`, а загрузчик сразу выходит при непустом списке. Поэтому изменения
с другого терминала не отражаются в уже открытом журнале. Аналогичный вызов после
прямого создания списания также не обновляет заполненный список.

Доказательство: установлено по цепочке обработчика WebSocket и раннего возврата;
тест F02 дополнительно показывает, что повторный обычный LoadDocuments не делает
запрос. Живое WebSocket-соединение отдельно не воспроизводилось.

Исправление: явно инвалидировать кэш при внешнем изменении и после мутаций;
отделить повторное открытие экрана от запроса актуализации.

### F09 · P2 · Форма приёмки закрывается до результата сохранения

Место: `frontend/lib/features/inventory/view/widgets/warehouse/dialogs/receive_document/receive_document_processor.dart:120` и `:129`.

`saveDocument` добавляет событие в BLoC и немедленно закрывает диалог. Внешний
`await` ждёт только постановки события, не ответа сервера. При сетевой ошибке,
ошибке валидации или запрете сервера введённые строки уже уничтожены вместе
с контроллерами, пользователь не может поправить документ и повторить сохранение.

Доказательство: установлено по цепочке `ReceiveDocumentDialog._save` →
`ReceiveDocumentProcessor.saveDocument` → асинхронный обработчик DocumentBloc.
Отдельный виджет-тест этой формы не добавлялся.

Исправление: закрывать диалог по подтверждённому успеху конкретной операции;
при ошибке сохранять форму и показывать сообщение рядом с действием.
