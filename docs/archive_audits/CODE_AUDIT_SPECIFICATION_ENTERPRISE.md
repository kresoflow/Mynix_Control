# 🛡️ Техническое Задание: Комплексный Аудит Качества Кода, Архитектуры и Безопасности

> **Назначение:** Регламент и инструкция для проведения независимого аудита кодовой базы ИИ-агентами (LLM-auditors) и ведущими Senior / Tech Lead инженерами.  
> **Цель:** Объективная оценка уровня зрелости системы, выявление скрытых уязвимостей, архитектурных антипаттернов («говнокода»), определение реального грейда разработчиков и формирование приоритизированной дорожной карты (Action Plan).

---

## 1. Регламент и Правила Проведения Аудита (Evidence-Based Rule)

1. **Никакой воды и субъективных мнений:** Каждая выявленная проблема **обязана** содержать:
   * Точный путь к файлу и номера строк (`path/to/file.ext:L12-L34`).
   * Категорию риска (P0 Blocker, P1 Critical, P2 Major, P3 Minor).
   * Описание вектора атаки / сбоя (Что сломается при нагрузке или атаке?).
   * Эталонный пример исправления (Before / After diff).
2. **Нулевая терпимость к скрытому долгу:** Не допускается игнорирование временных костылей (`TODO`, `FIXME`, `HACK`, отключенные проверки линтеров).
3. **Статический + Логический анализ:** Проверяется не только факт компиляции, но и поведение системы под конкурентной нагрузкой, сбоями сети и невалидными данными.

---

## 2. Программа Аудита (Scope of Inspection)

### 🧱 Блок 1: Архитектурный Аудит (Architecture Review)

#### 1.1 Backend (FastAPI / Python / SQLModel / PostgreSQL)
* [ ] **Separation of Concerns:** 
  * Роутеры (`routers/`) содержат **только** HTTP-маппинг, валидацию Pydantic и инжекцию `Depends()`. 
  * Бизнес-логика, транзакции и обращение к БД вынесены в `services/`.
* [ ] **Data Access & N+1 Prevention:**
  * Проверка всех ORM-запросов к связанным сущностям на использование eager loading (`selectinload` / `joinedload`).
  * Контроль использования асинхронных сессий (`asyncpg`), отсутствие синхронных блокировок сессий.
* [ ] **Multi-Tenancy & Data Isolation:**
  * Аудит изоляции данных: проверка использования схем (`PostgreSQL Schemas`) или строгой фильтрации.
  * Полное отсутствие риска случайной утечки данных между тенантами при конкурентных запросах.
* [ ] **Micro-Architecture:**
  * Отсутствие "God Objects" (файлы > 250–300 строк должны быть декомпозированы).
  * Отсутствие циклических зависимостей между доменами.

#### 1.2 Frontend (Flutter / Dart / BLoC)
* [ ] **Macro-Architecture:** Строгое соблюдение Feature-Driven структуры (`lib/features/<module>/`).
* [ ] **State Management & Purity:**
  * Запрет бизнес-логики и HTTP-запросов внутри `StatefulWidget` и UI-слоя.
  * Управление состоянием только через BLoC / Cubit с иммутабельными стейтами (`Equatable`).
* [ ] **UI Decomposition:**
  * Длина файлов UI не превышает 200–250 строк.
  * Вложенные `build()` методы и комплексные модалки вынесены в отдельные виджеты в `widgets/`.
* [ ] **Networking & DI:**
  * Прямые вызовы HTTP-клиента из UI запрещены. Все вызовы идут через `RepositoryProvider` и настроенный `ApiClient`.

---

### 🔒 Блок 2: Аудит Безопасности (Security & OWASP Top 10)

* [ ] **Контроль доступа (PBAC / RBAC):**
  * 100% покрытие всех приватных эндпоинтов проверкой прав `Depends(require_permission(...))`.
  * Проверка на горизонтальное повышение привилегий (IDOR): может ли пользователь одного тенанта запросить сущность другого тенанта по прямому ID?
* [ ] **Аутентификация и Токены:**
  * Валидация алгоритмов подписи JWT, проверка сроков жизни (`exp`), безопасное хранение секрета.
  * Хранение паролей и PIN-кодов исключительно в виде стойких хешей (bcrypt/argon2).
* [ ] **Инъекции и Валидация Ввода:**
  * Отсутствие raw SQL с f-string интерполяцией.
  * Строгие Pydantic-схемы без нетипизированных `dict` / `Any` в payload.
* [ ] **Secrets & Repo Hygiene:**
  * Отсутствие захардкоженных API-ключей, токенов и паролей в кодовой базе.
  * Наличие `.env` в `.gitignore`.

---

### ⚡ Блок 3: Надежность, Асинхронность и Качество Кода (Clean Code)

* [ ] **Async Event-Loop Safety:**
  * Поиск блокирующего синхронного I/O в async-функциях (`time.sleep`, `open()`, `requests.get`, `urllib.request`).
* [ ] **Обработка Исключений (Resilience):**
  * Отсутствие "слепых" `except Exception: pass` и неконтролируемых падений с HTTP 500.
  * Использование кастомной иерархии доменных исключений (`AppException` ➔ 400, 403, 404, 409).
* [ ] **DRY & Dead Code:**
  * Поиск дублирования бизнес-логики и UI-компонентов.
  * Поиск неиспользуемого или закомментированного кода.

---

### 🚢 Блок 4: DevOps, Тестирование и Инфраструктура

* [ ] **Автоматизированное тестирование:**
  * Наличие Unit и Integration тестов для критических путей (авторизация, биллинг, склад).
  * Корректная изоляция тестового окружения (фикстуры БД, моки внешних сервисов).
* [ ] **CI/CD Пайплайны:**
  * Наличие автоматических проверок (линтеры, тесты, сборка Docker) при каждом Pull Request / Push.
* [ ] **Безопасность Контейнеризации:**
  * Запуск сервисов в Docker от non-root пользователя (`USER appuser`).
  * Наличие `HEALTHCHECK` и оптимизированный многоэтапный билд (multi-stage).

## 3. Матрица Объективной Оценки Зрелости (Seniority Level)

По результатам проверки кодовой базе и разработчикам присваивается объективный грейд:

| Грейд | Характеристики Кода и Архитектуры |
|---|---|
| **Junior** | • Логика смешана с UI / роутерами, прямые SQL в эндпоинтах.<br>• Хардкод настроек и текстов, секреты в репозитории.<br>• Нет обработки ошибок (500 ошибки), блокирующий I/O в async.<br>• Отсутствуют тесты и CI/CD. Репозиторий забит временными скриптами. |
| **Middle** | • Архитектура разделена на слои (Routers / Services / Repositories).<br>• Присутствуют "God Objects" (>300 строк), есть проблема N+1 запросов.<br>• Базовая безопасность (JWT, базовый RBAC), но есть пробелы в edge-cases.<br>• Тесты есть, но хрупкие или требуют ручного запуска. Базовый Docker. |
| **Senior** | • Чистая архитектура, SOLID, строгая декомпозиция (модули ≤200 строк).<br>• Secure by design: 100% PBAC, защита от IDOR, строгая изоляция данных.<br>• Высокая асинхронная производительность, идеальный eager loading.<br>• Полный CI/CD пайплайн, Docker non-root, надежный test suite. |
| **Staff / Lead Architect** | • Все критерии Senior + промышленная multi-tenant инфраструктура.<br>• Распределенная отказоустойчивость, идемпотентность API.<br>• Высокая наблюдаемость (Observability: structured logging, tracing, metrics).<br>• Документированные ADR (Architecture Decision Records). |

## 4. Ожидаемый Результат: Структура `audit_report.md`

Итоговый отчет аудитора должен содержать следующие разделы:

1. **Executive Summary:** Общая оценка зрелости (Junior / Middle / Senior / Staff) с подробным обоснованием.
2. **Таблица метрик:**
   * Количество файлов > 250 строк.
   * Процент эндпоинтов с PBAC.
   * Количество блокирующих вызовов в Event Loop.
   * Статус прохождения автотестов и линтеров.
3. **Реестр Уязвимостей и Дефектов (Categorized Findings):**
   * **P0 Blocker (Уязвимости безопасности / Утечки данных):** файл, строка, риск, фикс.
   * **P1 High (Архитектурные сбои, N+1, God Objects):** файл, строка, риск, фикс.
   * **P2 Medium (Качество кода, дублирование, плохой error handling):** файл, строка, фикс.
   * **P3 Low (Стиль, линтеры, предупреждения компилятора):** файл, строка.
4. **Пошаговая Дорожная Карта Рефакторинга (Action Plan):**
   * Приоритизированные фазы устранения дефектов с оценкой трудоемкости.
