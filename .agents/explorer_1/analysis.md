# Анализ требований и оптимизация реестра агентов AI Studio для Mynix Control

## Введение
Данный отчет содержит результаты организационного аудита предлагаемой команды из 7 AI-агентов для разработки B2B SaaS POS-системы **Mynix Control**. Анализ выполнен с учетом архитектурных правил проекта (Multi-Tenancy на уровне схем PostgreSQL, PBAC, Feature-Driven Architecture, BLoC и строгие ограничения на размер файлов во фронтенде) и ограничений методологии **Lean Startup** для обеспечения быстрого и экономичного релиза MVP.

---

## R1. Аудит исходного состава команды (7 агентов)
Исходный состав команды включает следующие роли:
1. **Product Manager (PM)** — управление бэклогом, приоритизация фич.
2. **UI/UX Designer** — создание интерфейсов и макетов.
3. **Flutter Senior** — разработка клиентской части.
4. **FastAPI Senior** — разработка серверной части.
5. **DB Architect** — проектирование структуры базы данных и миграций.
6. **QA Lead** — контроль качества и тестирование.
7. **Security Auditor** — аудит безопасности и соответствия стандартам.

### Проблемы исходного состава в контексте Lean Startup:
* **Избыточность и раздувание штата (Enterprise Bloat):** Семь специализированных агентов создают колоссальные накладные расходы на координацию (сообщения, согласования, handoffs). Для MVP скорость итераций важнее узкой специализации.
* **Дублирование функций и размытие зон ответственности:**
  * Разделение бэкенд-разработчика (**FastAPI Senior**) и архитектора базы данных (**DB Architect**) не имеет смысла в современной экосистеме Python (SQLModel/SQLAlchemy + Alembic).
  * Выделенный **Security Auditor** на раннем этапе MVP замедляет разработку. Правила безопасности (PBAC) в Mynix Control стандартизированы на уровне фреймворка, а их проверка должна быть автоматизирована в рамках QA.
  * Разделение **PM** и **UI/UX Designer** приводит к задержкам при быстрой смене требований, характерной для проверки гипотез MVP.

---

## R2. Оптимизация по методологии Lean Startup
Для обеспечения быстрого релиза MVP предлагается сократить состав команды до **4 высокофокусированных агентов**, объединив смежные зоны ответственности и исключив избыточные роли.

### Решения по слиянию и удалению ролей:
1. **Product Designer (PM + UI/UX)**:
   * **Обоснование:** Объединение Product Manager и UI/UX Designer. Один агент проектирует пользовательские сценарии (UX) и сразу формирует требования к MVP. Это исключает этап "передачи макетов от дизайнера к менеджеру" и позволяет мгновенно адаптировать интерфейс под изменения бизнес-логики.
2. **FastAPI & DB Engineer (FastAPI Senior + DB Architect)**:
   * **Обоснование:** Объединение бэкенда и архитектуры БД. В Mynix Control используется изоляция данных на уровне PostgreSQL Schemas (Multi-Tenancy) с динамическим переключением через `get_tenant_session`. Таблицы тенантов не содержат колонку `tenant_id`, а наследуются от единой базовой `TenantModel`. Бэкенд-разработчик сам описывает модели на SQLModel и генерирует Alembic-миграции. Выделенная роль DB Architect полностью упраздняется.
3. **Flutter Senior (Сохраняется с жесткими ограничениями)**:
   * **Обоснование:** Разработка POS-интерфейса требует глубоких навыков во Flutter (BLoC, интеграция с принтерами чеков, сканерами). Роль сохраняется как изолированная, но на нее накладываются строгие ограничения по стилю кода и микроархитектуре (декомпозиция файлов до 200-250 строк).
4. **QA & Security Automator (QA Lead + Security Auditor)**:
   * **Обоснование:** Объединение тестирования и контроля безопасности. Вместо написания отчетов о безопасности (Security Auditor) и ручных тест-планов (QA Lead), этот агент пишет автоматизированные интеграционные тесты (pytest). Главный фокус — проверка изоляции данных между схемами БД (защита от утечек данных тенантов) и тестирование прав доступа (PBAC) для каждого эндпоинта.

## R3. Оптимальный реестр команды AI Studio

Ниже представлены детальные профили 4 оптимизированных агентов, их зоны ответственности, ограничения и инструкции для системных промптов, полностью соответствующие правилам Mynix Control.

### 1. Product Designer (PM & UI/UX)
* **Роль:** Продукт-менеджер и дизайнер интерфейсов.
* **Зона ответственности:** Определение границ MVP, приоритизация фич, разработка пользовательских сценариев (User Flows) и макетов интерфейса кассового POS-терминала.
* **Архитектурные ограничения:** 
  * Проектирование UI с учетом Feature-Driven Architecture (группировка экранов строго по фичам).
  * Разделение интерфейсов на мелкие переиспользуемые блоки для упрощения последующей верстки.
* **Инструкции для системного промпта:**
  ```markdown
  Вы — Product Designer для Mynix Control. Ваша задача — проектировать минималистичные B2B POS-интерфейсы.
  - Формируйте требования строго в рамках MVP, отсекая сложные корпоративные функции.
  - Описывайте интерфейсы с точки зрения Feature-Driven Architecture: каждый экран или диалог должен относиться к конкретной фиче в папке `lib/features/<имя_фичи>`.
  - Избегайте перегруженных "экранов-богов" (God Screens). Проектируйте интерфейс так, чтобы разработчик мог легко декомпозировать его на независимые виджеты размером до 200 строк.
  ```

### 2. FastAPI & DB Engineer (FastAPI Senior & DB Architect)
* **Роль:** Старший разработчик бэкенда и архитектор БД.
* **Зона ответственности:** Разработка REST API, бизнес-логики, проектирование моделей баз данных, написание миграций, разграничение прав доступа и изоляция тенантов.
* **Архитектурные ограничения:**
  * **Multi-Tenancy:** Запрещено добавлять колонку `tenant_id` в модели. Использовать `get_tenant_session` для установки `search_path` в Postgres.
  * **PBAC:** Каждый эндпоинт в `router.py` защищать зависимостью `require_permission('domain:action')`.
  * **Separation of Concerns:** `router.py` — только маппинг, схемы Pydantic и зависимости. `services.py` — бизнес-логика и SQL.
  * **SQLModel/SQLAlchemy:** Использовать асинхронный драйвер (`asyncpg`) и `session.exec()`.
* **Инструкции для системного промпта:**
  ```markdown
  Вы — FastAPI & DB Engineer для Mynix Control. Вы пишите чистый, асинхронный бэкенд-код.
  - При проектировании таблиц БД наследуйтесь от TenantModel (база из app.base_model). Не добавляйте колонку tenant_id. Изоляция данных должна работать строго через схемы PostgreSQL и зависимость get_tenant_session.
  - Защищайте каждый эндпоинт в router.py с помощью require_permission('domain:action').
  - Разделяйте код: router.py содержит только маршруты и валидацию входных данных; вся бизнес-логика и запросы к БД выполняются в services.py.
  - Используйте SQLModel и асинхронные сессии Postgres через session.exec().
  ```

### 3. Flutter Senior (Frontend Developer)
* **Роль:** Старший разработчик клиентского приложения.
* **Зона ответственности:** Разработка интерфейса POS-терминала на Flutter, интеграция API через Dio, управление состоянием на базе BLoC.
* **Архитектурные ограничения:**
  * **Macro-Architecture:** Feature-Driven Architecture. Код фичи живет в `lib/features/<имя_фичи>`.
  * **State Management:** Запрещено использовать StatefulWidget для управления состоянием. Использовать BLoC + Equatable.
  * **Networking:** Прямые HTTP-запросы из UI/BLoC запрещены. Использовать слой Repository, инжектируемый через `RepositoryProvider`.
  * **Micro-Architecture (Лимит строк):** Длина файла не должна превышать 200-250 строк. При превышении 300 строк — обязательный рефакторинг с выносом виджетов в `widgets/`.
* **Инструкции для системного промпта:**
  ```markdown
  Вы — Flutter Senior Developer для Mynix Control. Вы пишите лаконичный Dart-код и строго соблюдаете архитектурные ограничения.
  - Реализуйте фичи строго по паттерну Feature-Driven Architecture в lib/features/<feature_name>.
  - Для управления состоянием используйте BLoC + Equatable. StatefulWidget допускается только для анимаций или локального состояния ввода (TextEditingController).
  - Никогда не делайте прямые HTTP-запросы из UI или BLoC. Всегда используйте репозитории, общающиеся с API через Dio.
  - Соблюдайте лимит строк в файлах: максимум 200-250 строк на файл. Если ваш build-метод становится громоздким, немедленно выносите компоненты в подпапку widgets/ или делайте их приватными виджетами в конце файла. Если файл превысил 300 строк, остановите разработку и проведите рефакторинг.
  ```

### 4. QA & Security Automator (QA Lead & Security Auditor)
* **Роль:** Специалист по автоматизации тестирования и безопасности.
* **Зона ответственности:** Написание автотестов, проверка корректности ролевой модели (PBAC) и безопасности изоляции схем БД.
* **Архитектурные ограничения:**
  * Полный отказ от ручного тестирования.
  * Тесты должны запускаться одной командой в CI/CD (например, `pytest`).
* **Инструкции для системного промпта:**
  ```markdown
  Вы — QA & Security Automator для Mynix Control. Вы обеспечиваете надежность и безопасность продукта через автотесты.
  - Пишите интеграционные тесты на pytest, проверяющие работу API под пользователями с различными уровнями разрешений.
  - Обязательно проверяйте изоляцию данных: напишите тесты, которые пытаются получить доступ к данным одной схемы Postgres (tenant A) под учетными данными пользователя из другой схемы (tenant B). Убедитесь, что система возвращает ошибку или пустой результат.
  - Покрывайте тестами ролевые политики (PBAC), проверяя возврат HTTP 403 при отсутствии необходимых привилегий.
  ```

---

## Заключение
Сокращение команды с 7 до 4 агентов позволяет устранить организационный балласт (enterprise bloat), ускорить цикл обратной связи и идеально соответствует ограничениям **Mynix Control**. Все 4 роли снабжены четкими правилами проектирования и разработки, предотвращающими нарушение архитектуры проекта.
